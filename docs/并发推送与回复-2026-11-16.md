# 并发推送与自动回复 — 2026-11-16

场景：同一个微信号被好几堆人下注，**同一秒多个群一起推**。服务端是
`app.run(threaded=True)`，每个请求一个线程，所以这里是真并发，不是排队。

要回答的是三件事：会不会**丢账**、会不会**多记账**、回复会不会**漏发或发错群**。

## 查出来的四个问题（都已修）

### 1. 生肖表缓存的竞态 —— 真丢账

`current_zodiac_mapping()` 原来的写法是：

```python
if _zodiac_cache["day"] != today:
    _zodiac_cache["day"] = today          # 先把日期写上
    _zodiac_cache["value"] = get_current_lunar_year()   # 再算值
return _zodiac_cache["value"][2]
```

两个线程同时进来：A 写好了 `day`、正算值；B 看到 `day` 是今天、`value` 还是
`None` → `TypeError: 'NoneType' object is not subscriptable` → 整条请求 500。
**那一批消息全丢**，采集端看到 500 会重试，但这几秒里客户已经以为记上了。

实测复现：8 个群并发，其中一个请求 500，记账 21/24，看板金额 2100 而不是 2400。

修法：加锁 + 先算好值再认日期（别的线程不会读到半成品）。

```python
v = get_current_lunar_year()
_zodiac_cache["value"] = v     # 先给值
_zodiac_cache["day"] = today   # 再认日期
```

### 2. 去重记录并发写同一个 `.tmp` —— 多记账隐患

`_save_processed()` / `_save_fingerprints()` 的临时文件是固定名
`processed_ids.json.tmp`。两个线程同时保存时日志里会出现：

```
保存去重记录失败：Permission denied ...
保存去重记录失败：[WinError 32] 另一个程序正在使用此文件 ...
```

去重记录没落盘 → 进程重启后，这一批消息不在"已处理"名单里 →
**同一批重推会被当成新消息再记一遍账**。

修法：抽 `_atomic_write_json()`，临时名带 `pid.线程号`，并加 `_PERSIST_LOCK`。

### 3. `is_message_processed` + `mark_message_processed` 两步之间的缝

先查后标，中间没有锁：同一 `msg_id` 的两条推送同时进来，两边都查到"没处理过"，
于是各记一次账。改成 `claim_message()` 一次做完（查 + 占位），只有一个线程能拿到 True。

跨账号的指纹判重同理，原来 `is_fingerprint_seen` + `mark_fingerprint` 也是两步，
两个微信号监听同一个群时同一条内容会被记两笔。改成 `claim_fingerprint()`。

### 4. 群名取不到时静默不回 —— 漏回复

原来只在 `if chat:`（群名非空）时才生成回执。客户刚拉群、名字还没同步过来，
账记上了但**客户收不到回执**。改成只要 `chat` 或 `chat_id` 有一个就回。

## 采集端回复侧（原本设计是对的，只补了一处）

`replier.send_all()` 的行为逐条验过：

- **串行发**：`_lock` + `interval` 间隔，注释写明"上一条刚发完等一会儿，微信窗口来不及切换就会串会话"
- **一条只发一次**：用 `msg_id` 做 key，失败也记下来不重试 —— 宁可漏一条，不能同一条发两遍
- **重名会话不瞎发**：清单里有两个同名群时直接跳过，避免把回复打到别人窗口

补的一处：`_save_replied()` 也是固定 `.tmp`，跟服务端同款隐患，改成唯一临时名 + 锁。

## 仍然存在的取舍（写清楚）

1. **同名群不回复**。微信只能按会话名找人，两个群同名时会跳到别人窗口，
   所以采集端选择跳过并记日志 —— 这是"宁可漏回，不能发错人"。
2. **回复失败不重试**。失败会写进 `replied.json` 和日志，但不会自动重发。
   重发同一条的代价是客户看到两遍"已记账"，比漏一条更像事故。
3. **回复靠会话名定位，不用 chat_id**。微信没有按 id 发消息的接口，
   `chat_id` 只用来排查是哪一条。
4. **账本写入本身有 `DATA_LOCK`**，同一账号的多笔并发是串行累加的，不会互相覆盖
   （日志里 `累计 $100 / $200 / $300` 是连续的）。

## 补充一：IP 白名单里的 localhost / 127.0.0.1（2026-11-16 追加）

绝大多数客户是**服务端和采集端装在同一台电脑**，所以「白名单怎么写才不会被自己挡掉」
是安装环节第一个坑。实测（`build\check_ip_allow.py`）：

| 白名单写的 | 采集端连的地址 | 修复前 | 修复后 |
|---|---|---|---|
| `127.0.0.1` | `127.0.0.1` | 200 | 200 |
| `127.0.0.1` | `localhost` | 200（靠回落） | 200 |
| `localhost` | `127.0.0.1` | **401** | **200** |
| `localhost` | `localhost` | **401** | **200** |
| `::1` | `127.0.0.1` | **401** | **200** |
| `127.0.0.0/8` | `::1` | **401** | **200** |
| `10.0.0.0/8` | `127.0.0.1` | 401 | 401（该拒的还拒） |

原因与修法：

- 本机 `localhost` 的解析顺序实测是 **IPv6 在前**（`::1` → `127.0.0.1`）。服务端默认绑
  `0.0.0.0` 只监听 IPv4，所以 `localhost` 会先试 `::1` 失败再回落，看起来「能用」，
  实际上每连接一次都多失败一次；服务端哪天改绑 `::`（双栈），`localhost` 就直接以
  `::1` 进来，只写 `127.0.0.1` 必被拒。
- 修复前 `ip_allowed()` 只做纯 IP/CIDR 比对，`localhost` 这种域名写法解析抛
  `ValueError` 后被 `continue` 跳过，等于这条**白写**——客户以为是自己的问题。
- 现在 `ip_allowed()` 把回环当一家人：`127.0.0.1` / `::1` / `localhost` / 回环网段
  （如 `127.0.0.0/8`）互相都认，来源是这两个地址里的任一个就放行；非回环网段
  （`10.0.0.0/8` 等）仍然按原样严格比对，不会被本机地址蹭过去。

**给客户的填写建议**：本机部署写 `127.0.0.1` 就够（现在 `::1` 也认）。
如果采集端在另一台电脑，必须填那台机器的**实际出口 IP**，不能写 `127.0.0.1`。

## 补充二：服务端响应慢（要问大模型）时的回执（2026-11-16 追加）

采集端 `timeout` 是 8 秒，而一条规则吃不下的消息（连肖、部分 12/13/14 写法）要等服务端
调模型，十几秒很正常。实测（`build\check_slow_response.py`，假模型故意拖 15 秒）：

```
第 1 次推送      → 8.0 秒超时，采集端判失败
立刻重试同一条   → 0.0 秒，服务端答 pending（还在算）
再等 2 秒重试    → 0.0 秒，仍然 pending
模型返回         → 记账成功 ¥200
再来取一次       → 拿到 1 条回执：「0个号 共计200」
```

修复前的行为是：重试那次 200 里 `replies` 为空，采集端把它当成功就再不管了 ——
**账记上了，客户永远收不到回执**。这是「不丢账、不多记、但漏回复」的根因。

修法（**没有加大 timeout**，避免消息多时推送线程被慢请求拖住）：

1. 服务端给每个 `msg_id` 留一份回执（`_reply_cache`，最近 500 条），并把正在解析的
   消息号记进 `_pending_msgs`。
2. 重推撞上 `claim_message` 时按状态分流：
   - `pending` → 响应体带 `"pending":[msg_id]`，让采集端知道「还没算完」；
   - 已算完 → 把当初那份回执放进 `replies` 一起返回（补发）；
   - 早处理完且缓存过期 → 照旧当重复跳过。
3. 采集端 `pusher._send` 看到 `pending` 就不算成功，按原有退避
   （`BACKOFF = [2,4,8,16,30,60,120,300]`）再来取，最多到 `max_retry`。
   一直取不到回执时**不进死信**（进死信会让客户重发，那会重复记账），
   只把消息状态记成「已送达，回执未回」并写警告日志。

实测覆盖：服务端 `check_slow_response.py` 9 项、采集端
`tools\check_pending_retry.py` 8 项全过。

取舍（写清楚）：

- **超时仍是 8 秒**。加大超时的代价是每条慢消息都占住推送线程，一批 20 条串行等下去
  就是几分钟不推新消息，用户担心的「消息多时瘫痪」会真的发生。用「pending + 短超时 +
  退避重取」换同样的效果，占用时间反而更短。
- **重试窗口有上限**：`max_retry=8` 配退避累计约 9 分钟。超过这个窗口还没拿到回执，
  多半是服务端已经死了，这时提示「回执未回」比无声丢弃强。
- **补发回执只覆盖最近 500 条**。真重复（隔很久重发同一条）不会再触发补发，
  避免把旧回执当成新消息的回复发出去。
