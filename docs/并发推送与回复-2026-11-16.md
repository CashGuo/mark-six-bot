# 并发推送与自动回复 — 2026-11-16

场景：同一个微信号被好几堆人下注，**同一秒多个群一起推**。服务端是
`app.run(threaded=True)`，每个请求一个线程，所以这里是真并发，不是排队。

要回答的是三件事：会不会**丢账**、会不会**多记账**、回复会不会**漏发或发错群**。

## 查出来的四个问题（都已修）

### 1. 生肖表缓存的竞态 —— 真丢账

`current_zodiac_mapping()` 原来的写法是：

```python
if _zodiac_cache["day"] != today:
    _zodiac_cache["day"] = today          # 先把日期写上
    _zodiac_cache["value"] = get_current_lunar_year()   # 再算值
return _zodiac_cache["value"][2]
```

两个线程同时进来：A 写好了 `day`、正算值；B 看到 `day` 是今天、`value` 还是
`None` → `TypeError: 'NoneType' object is not subscriptable` → 整条请求 500。
**那一批消息全丢**，采集端看到 500 会重试，但这几秒里客户已经以为记上了。

实测复现：8 个群并发，其中一个请求 500，记账 21/24，看板金额 2100 而不是 2400。

修法：加锁 + 先算好值再认日期（别的线程不会读到半成品）。

```python
v = get_current_lunar_year()
_zodiac_cache["value"] = v     # 先给值
_zodiac_cache["day"] = today   # 再认日期
```

### 2. 去重记录并发写同一个 `.tmp` —— 多记账隐患

`_save_processed()` / `_save_fingerprints()` 的临时文件是固定名
`processed_ids.json.tmp`。两个线程同时保存时日志里会出现：

```
保存去重记录失败：Permission denied ...
保存去重记录失败：[WinError 32] 另一个程序正在使用此文件 ...
```

去重记录没落盘 → 进程重启后，这一批消息不在"已处理"名单里 →
**同一批重推会被当成新消息再记一遍账**。

修法：抽 `_atomic_write_json()`，临时名带 `pid.线程号`，并加 `_PERSIST_LOCK`。

### 3. `is_message_processed` + `mark_message_processed` 两步之间的缝

先查后标，中间没有锁：同一 `msg_id` 的两条推送同时进来，两边都查到"没处理过"，
于是各记一次账。改成 `claim_message()` 一次做完（查 + 占位），只有一个线程能拿到 True。

跨账号的指纹判重同理，原来 `is_fingerprint_seen` + `mark_fingerprint` 也是两步，
两个微信号监听同一个群时同一条内容会被记两笔。改成 `claim_fingerprint()`。

### 4. 群名取不到时静默不回 —— 漏回复

原来只在 `if chat:`（群名非空）时才生成回执。客户刚拉群、名字还没同步过来，
账记上了但**客户收不到回执**。改成只要 `chat` 或 `chat_id` 有一个就回。

## 采集端回复侧（原本设计是对的，只补了一处）

`replier.send_all()` 的行为逐条验过：

- **串行发**：`_lock` + `interval` 间隔，注释写明"上一条刚发完等一会儿，微信窗口来不及切换就会串会话"
- **一条只发一次**：用 `msg_id` 做 key，失败也记下来不重试 —— 宁可漏一条，不能同一条发两遍
- **重名会话不瞎发**：清单里有两个同名群时直接跳过，避免把回复打到别人窗口

补的一处：`_save_replied()` 也是固定 `.tmp`，跟服务端同款隐患，改成唯一临时名 + 锁。

## 仍然存在的取舍（写清楚）

1. **同名群不回复**。微信只能按会话名找人，两个群同名时会跳到别人窗口，
   所以采集端选择跳过并记日志 —— 这是"宁可漏回，不能发错人"。
2. **回复失败不重试**。失败会写进 `replied.json` 和日志，但不会自动重发。
   重发同一条的代价是客户看到两遍"已记账"，比漏一条更像事故。
3. **回复靠会话名定位，不用 chat_id**。微信没有按 id 发消息的接口，
   `chat_id` 只用来排查是哪一条。
4. **账本写入本身有 `DATA_LOCK`**，同一账号的多笔并发是串行累加的，不会互相覆盖
   （日志里 `累计 $100 / $200 / $300` 是连续的）。
