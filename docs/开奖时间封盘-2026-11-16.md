# 开奖时间封盘（2026-11-16）

每期都有一个开奖时间（一般是 21:00 / 21:30 之类），过了这个点这期就不该再收注。
以前服务端只认"自然日 0 点换期"，周二 21:30 开奖之后到 24:00 收到的注还会照常记进周二期，
账就对不上。这次把"当晚几点封盘"补上。

## 一、定下来的规则（老板拍板）

| 问题 | 结论 |
| --- | --- |
| 开奖时间怎么设 | 配置页一项 `HH:MM`，**固定值、每期都一样**，不做按期单独设 |
| 开奖日 | 不变，仍是**周二 / 周四 / 周六**（`DRAW_WEEKDAYS = (1, 3, 5)`） |
| 封盘后客户发来的注 | **记录消息，但不记账**，还要回一句"本期已开奖，这单没记上" |
| 老客户兼容 | 没有老客户，默认直接 `21:30`，不做迁移 |
| 手工记账 | 网页清单、手工文本**都不受限制**（老板要能补录） |

静默丢弃是不行的：以前漏回执吃过亏，客户以为记上了，开奖后对不上账。
所以封盘拒单时必须回执，且要让采集端把它当正常回执发出去。

## 二、期次与封盘点

- 期号 = **开奖日**的日期（`issue_of()`）：从收到消息那天（含）往后找最近的开奖日。
  周一收到的注归周二那期，周日收到的归下周二那期。
- 封盘点 = **本期的开奖日 + 配置的开奖时间**。例如本期 `2026-11-17`、开奖时间 `21:30`
  → 封盘点 `2026-11-17 21:30`。
- 判定：`now >= 封盘点` 即封盘。
- 换期仍靠自然日 0 点：次日 `00:00` 之后 `issue_of()` 自然指向下一个开奖日，
  封盘点也跟着跳到下一期 —— 所以"次日自动进下一期"不需要额外定时器。

**推论（容易误会的点）**：封盘只发生在**开奖日当晚**。
周一/周三/周五/周日这两天，本期开奖日还在未来（周二/周四/周六），此时永远不封盘，
这是对的 —— 客户周日晚下的注本来就是买周二那期。

## 三、代码位置

### 判定（`main.py`）

| 名字 | 作用 |
| --- | --- |
| `_as_dt(ts)` | 解析消息时间，**保留时分**（认 epoch / 多种字符串格式）；认不出退回 `datetime.now()` |
| `DRAW_TIME_DEFAULT = "21:30"` | 默认值 |
| `_parse_hhmm(s)` | 认 `21:30` / `9:30` / `2130` |
| `DRAW_TIME_RAW` / `DRAW_TIME` | 模块级读配置；解析失败回落 `21:30` 并 `logger.warning` |
| `draw_cutoff_state(at=None)` | 返回 `{issue, draw_time, close_at, closed, now}` |

`draw_cutoff_state` 传 `at` 时按**消息时间**判（采集端补推、消息堆积都靠这个），
不传就按服务器当前时间判（看板、手工入口用）。

### 三个记账入口的差异

| 入口 | 是否受封盘限制 | 原因 |
| --- | --- | --- |
| `/wx/hook`（微信推送） | **受限制** | 客户实时下的注，开奖后不该再进这一期 |
| `/api/manual/submit`（网页清单） | 不受限制 | 老板补录 |
| `/api/quick_bet`（手工文本） | 不受限制 | 老板补录 |

实现：`record_bet(..., allow_after_close=False)` 在解析前加闸门，封盘时返回
`{"ok": False, "closed": True, "reason": "本期已开奖（21:30）"}`；
两个手工入口传 `allow_after_close=True`。

### `wx_hook` 的拒单分支

`r.get("closed")` 为真时：

1. `skipped += 1`，消息流水写一行 `跳过 / 本期已开奖（21:30）` —— **留痕**，老板能查为什么没记；
2. `unmark_fingerprint(fp)` —— 这条没记上账，客户在群里重发一遍应当还能被认，
   不能让内容指纹把重发判成"另一个号已经收过"；
3. 生成回执 `本期已开奖（21:30），这单没记上，下期再下`，进 `replies`
   （**也进回执缓存**，超时重推时能补发）；
4. `continue`，不记账、不碰账本。

`accepted += 1` 挪到了 `record_bet` 之后 —— 否则拒单也被算成"已受理"，看板数字虚高。

### 看板 `/api/dashboard`

新增 4 个字段：

| 字段 | 例子 | 用途 |
| --- | --- | --- |
| `draw_time` | `21:30` | 文案 |
| `closed` | `false` | 是否封盘 |
| `close_at` | `11-17 21:30` | 封盘点 |
| `seconds_left` | `7620` | 剩余秒数 |

`seconds_left` 由服务端算，前端只负责每秒递减 —— **不信任客户电脑的时钟**
（差几分钟就显示错误状态，比不显示更糟）。

### 界面

- `templates/dashboard.html`：顶部 chip `本期 2026-11-17 · 21:30 截止（剩 2 小时 10 分）`，
  封盘后变红加粗 `· 已封盘（21:30 开奖）`。1 秒一跳，归零时自动 `load()` 复核。
- `templates/manual.html`：封盘时 bar 上显示红字 `本期已开奖（21:30），现在记的是补录`，
  让老板知道自己在记哪一期。手工页本身不拦。

### 配置

- `msb_paths._DEFAULT_CONFIG`：`"draw_time": "21:30"`
- `server_gui.DEFAULTS`：同上
- 配置页新增「收注规则」组：开奖时间输入框 + 说明（填 `HH:MM`，开奖日仍是二/四/六，手工不受限）
- `save_cfg()` 校验：空值当 `21:30`；纯数字 3/4 位自动补冒号；非法值弹错误框并中止保存；
  填了上午的时间（`hh < 12`）会二次确认（多半是填错，上午就封盘等于整天不收注）

校验放在保存时而不是服务端兜底是有意的：服务端解析失败会静默回落 `21:30`，
客户会以为"我改的没生效"，比直接报错更难查。

## 四、验证

新增 `build/check_draw_cutoff.py`，16 项：

| 段 | 覆盖 |
| --- | --- |
| A（9 项） | 判定函数用固定日期断言：21:20 收 / 21:30 封 / 21:40 封 / 23:59 封 / 次日 00:10 进周四期并开 / 周一给周二那期收 / 周四、周六开奖后封 / 周日给下周二收 |
| B（6 项） | 消息时间 2026-11-14 21:40（周六开奖后）：不记账、回执含"已开奖"、金额不变、流水留痕、同内容重发仍按"已开奖"（不被指纹误判） |
| C（2 项） | 消息时间 2026-11-14 21:20（开奖前）：照常记账、回执是正常文案 |
| D（2 项） | 同一封盘时刻：推送口径拒（`closed=True`），`allow_after_close=True` 的手工口径记上 |

关键设计：**用 `create_time` 控制场景，不改系统时间**。
测试不依赖"今天星期几"、不依赖跑测试时是几点，随时都能跑。

实测结果：16 项全过。

## 五、坑与取舍

1. **不要拿"现在"去测封盘**。`draw_time` 设成 `00:01` 并不等于已封盘 ——
   周一的本期开奖日是周二，周二的 `00:01` 还在未来。第一版测试脚本就在这里翻车。
2. **采集端超时不加大**（仍是 8 秒）。封盘拒单的回执走的是原有的 `replies` 通道 +
   `_reply_cache`，跟正常记账的回执同一条路，不需要为了它加长超时。
3. **指纹要放回**。封盘拒单是"没记上账"，如果指纹留着，客户重发会被判成重复而静默跳过，
   客户既没收到回执也没记上账 —— 双重损失。
4. **`accepted` 只统计真记上的**。拒单计入 `skipped`，看板的"受理数"才对得上账。
5. 手工入口的 `allow_after_close=True` 是**故意**的。要是以后想收紧（比如只允许补录当天），
   得在那两个 handler 里单独判，不要动 `record_bet` 的默认值。
