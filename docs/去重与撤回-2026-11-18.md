# 去重窗口与客户撤回（2026-11-18）

## 1. 去重口径改成窗口

老板定的口径：**同一个群、同一个人、同样的正文，只算一次注**。真实的"发重了"常隔几秒，
所以指纹里不能再带发送时间——老实现是 `sha1(会话|create_time|发送人|正文)`，`create_time` 精确到秒，
隔 2 秒重发就记两笔。

现在：

```python
FINGERPRINT_WINDOW = 30   # 秒，窗口内重复到达只记一次
msg_fingerprint(chat_id, create_time, sender, content)  # create_time 不再进指纹
claim_fingerprint(fp, create_time)                      # 窗口按消息自己的时间算
```

- 指纹表结构改成 `{"v": 2, "items": {fp: 最近一次入账秒级时间}}`，保留 7 天（`FINGERPRINT_TTL`）；
  读到旧版本纯 list 文件直接清空（算法变了，留着也对不上）。
- 窗口判的是"这两条内容相隔多久"（`abs(ts - last)`），不是"离现在多久"——两台机器时钟有偏差也不影响。
- **取舍**：客户 0 秒、35 秒两次发同样内容，第二次会记（差 35 > 30）；但 0 秒、30 秒、35 秒三次，
  第三次（差的只有 5 秒）会被挡。这种极端情况按"老板说重发算重复"处理，可接受。

流水里的提示文案也从"另一个号已经收过"改成 **"这条重复了，只记一次"**（同账号重发也是这个原因，
不一定是另一个号收的）。

## 2. 客户撤回

### 2.1 数据从哪来

采集端把两条字段搬上来（`WxPushTool`）：

- 普通消息：`srv_id` = 微信服务端的消息 id（`MsgSvrID`）
- 撤回提示：`revoke_of` = 被撤那条的 `srv_id`（微信撤回消息里只有 `<newmsgid>`，拿不到原文）

### 2.2 服务端三分支（`main.py` → `handle_revoke()`）

`/wx/hook` 在 `SKIP_TYPES` 判断**之前**拦 `revoke_of`，所以撤回不会被当"系统消息"跳过。

| 情况 | 处理 | 流水里显示 |
|---|---|---|
| 已经记账了 | `find_msg_id_by_srv()` 按 srv_id 找到当初那笔 → `reverse_record()` 逐号冲正；同时作废这条的"已记账"回执（`drop_reply`），避免采集端超时重推又把"记上了"发给客户 | `已冲正`（橙字）+ `¥100` |
| 收到但没记账（正在等模型 / 已开奖 / 没解析出来） | 挂**预登记**，等它落账时拦住 | `撤回待核对`（灰字） |
| 压根还没到（撤回比原消息先到） | 挂预登记带 TTL（`REVOKE_PENDING_TTL = 600` 秒）；消息到了以后 `revoke_pending_for(srv_id)` 命中就直接跳过不记账 | `已撤回`（灰字） |

三条都不阻塞别的消息：预登记是内存 + 落盘的小表（`data/pending_revokes.json`），不占锁、不排队。

### 2.3 幂等

- 同一条撤回重复到达：第二次 `reverse_record()` 会返回"这笔已经撤销过了"，不重复扣。
- 撤回后客户重发同一条：`reverse_record()` 已经 `unmark_message_processed(msg_id)` +
  `unmark_fingerprint(fp)`，所以重发能重新入账。
- 攒在预登记里、超过 10 分钟仍没等到原消息的，自动清掉（那条消息多半是采集端没收到，转人工核对）。

### 2.4 界面

消息页对三种新结果做了区分（GUI 与网页一致）：

- `已冲正` → 橙色加粗（`warn` / `.warm`）——真金白银动了，不能和"跳过"一样用灰字
- `撤回待核对`、`已撤回` → 灰字（没动账）
- 被冲正的那条原记账行仍显示 `已撤销 · 原 记账 ¥100`，撤干净了也不会消失

## 3. 测试结果（2026-11-18）

**函数级 17/17 通过**（`test_server_revoke.py`，用 `MSB_HOME` 指到临时目录，不碰真实账本）

**HTTP 级 11/11 通过**（`test_http_revoke.py`，真进程 + HMAC 验签 + 真落盘）：

| 用例 | 结果 |
|---|---|
| 正常记账 | recorded=1，账本 25=100，流水存下 `srv_id=S10` |
| 同内容隔 2 秒重发 | recorded=0、skipped=1，账本仍是 100 |
| 撤回已记账的那条 | 账本 25 归零，`records.jsonl` 多一条 `type=reversal`、金额 -100 |
| 撤回一条还没到的（S99） | 落进 `pending_revokes.json` |
| 那条消息之后才到 | recorded=0，26 号没记上 |
| 之后再来正常消息 | recorded=1，27 号=30（链路没被改坏） |

## 4. 参数在哪调

| 参数 | 位置 | 默认 |
|---|---|---|
| 去重窗口 | `main.py` `FINGERPRINT_WINDOW` | 30 秒 |
| 指纹保留 | `main.py` `FINGERPRINT_TTL` | 7 天 |
| 撤回预登记等待 | `main.py` `REVOKE_PENDING_TTL` | 600 秒 |

## 5. 已知边界

- **撤回原文拿不到**：客户撤回后，微信只给 id。所以"撤的是哪条"能精确定位，但流水里撤回行只能显示
  `[撤回了一条消息]`，原内容看被冲正的那一行。
- **已开奖的账不能撤**：`reverse_record()` 拒绝跨期撤销（上期已归档结算）。
  这种撤回会落成"撤回待核对"，要人工处理——这是有意的，不能让归档和流水对不上。
- **采集端没开 / 断线期间的撤回会丢**：微信库里的 sysmsg 一旦没采到就补不回来，属于上游限制。
